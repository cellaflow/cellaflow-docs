# Quickstart

You will start the Cellaflow engine, install the Python SDK, run a checkout that
places an order, kill the process the instant after the order is placed, and
resume the same session. The order is placed once.

This is the example behind the quickstart on
[cellaflow.com](https://cellaflow.com/#quickstart). It is one file with no
dependencies beyond the SDK, and it also lives in the SDK repo at
[`examples/quickstart`](https://github.com/cellaflow/cellaflow-sdks/tree/main/examples/quickstart).

## Prerequisites

- Docker installed
- Python 3.9+

---

## Step 1. Start the Cellaflow engine

The engine is the durable state backend your agents connect to. Run it locally
with a single Docker command:

```bash
docker run -d \
  --name cellaflow \
  -p 50051:50051 \
  -p 9090:9090 \
  -e CELLAFLOW_ALLOW_UNAUTHENTICATED=true \
  ghcr.io/cellaflow/cellaflow:latest
```

Verify it is healthy:

```bash
curl http://localhost:9090/health/ready
# {"status":"ready"}
```

<Warning>
**`CELLAFLOW_ALLOW_UNAUTHENTICATED=true` is not optional here.** Without it, and
without a `CELLAFLOW_AUTH_TOKEN`, the engine refuses to start and the container
exits immediately:

```
No authentication token is configured, so every caller would be accepted.
Set CELLAFLOW_AUTH_TOKEN to require credentials, or set
CELLAFLOW_ALLOW_UNAUTHENTICATED=true to serve without them deliberately.
```

An unset token would accept every caller, and nothing in the process can tell a
laptop from a reachable host, so the engine makes you say which one it is rather
than guessing. For anything beyond local development, set a token instead. See
[Self-Hosting](/self-hosting#authentication).
</Warning>

<Tip>
The engine persists state to RocksDB inside the container, which is lost when the
container is removed. To keep it, mount a volume: add `-v $(pwd)/cellaflow-data:/data`
to the command above.
</Tip>

---

## Step 2. Install the Python SDK

Install the [`cellaflow`](https://pypi.org/project/cellaflow/) package from PyPI:

```bash
pip install cellaflow
```

## Step 3. Write the workflow

Create a file called `checkout_agent.py`:

```python checkout_agent.py
"""The landing-page quickstart: a step that places an order, and a crash on top of it.

    python checkout_agent.py                  # places the order, then the pod dies
    python checkout_agent.py <session-id>     # resumes -- does NOT place it again
    cat orders.log                            # one line for that session, both times

The ledger is append-only and every line carries its session id, because the
engine outlives any single run. A ledger that reset itself would disagree with
the engine the moment you resumed an older session, and then it could no longer
adjudicate anything.

The counter below lives INSIDE the tool body, so this script can only report
what actually happened rather than what it hopes happened.
"""

import os
import sys
import uuid
from pathlib import Path

from cellaflow import step, tool, workflow

LEDGER = Path("orders.log")

#: Every example honours this, so any of them can be pointed at an engine
#: somewhere else.
ENGINE = os.environ.get("CELLAFLOW_TARGET", "localhost:50051")

#: Incremented inside the tool body. Stays 0 when the step is replayed, because
#: a replayed step never enters its body.
EXECUTED = {"orders": 0}

#: Set before the workflow runs so the ledger line can name its session.
SESSION = {"id": ""}


def orders_for(session_id: str) -> list[str]:
    if not LEDGER.exists():
        return []
    return [
        line
        for line in LEDGER.read_text().splitlines()
        if line.startswith(session_id)
    ]


@tool(tool_name="place_order")
def place_order(order_id: str, total_cents: int) -> dict:
    """The irreversible one: the shop takes no idempotency key. Leased."""
    EXECUTED["orders"] += 1
    confirmation = f"ord_{uuid.uuid4().hex[:10]}"
    with LEDGER.open("a") as fh:
        fh.write(f"{SESSION['id']} {confirmation} {order_id} {total_cents}\n")
    print(f"   🛒 PLACED {order_id} for {total_cents} -> {confirmation}")
    return {"confirmation": confirmation, "total_cents": total_cents}


@step
def build_receipt(order: dict, order_id: str) -> dict:
    print("   🧾 Building receipt...")
    return {"order_id": order_id, "confirmation": order["confirmation"]}


@workflow(version="1.0.0", target=ENGINE)
def checkout(order_id: str, die_after_ordering: bool = False) -> dict:
    order = place_order(order_id, 2499)

    if die_after_ordering:
        # The order is placed and recorded; the receipt is not built yet.
        print("   💥 pod died")
        sys.stdout.flush()
        os._exit(17)

    return build_receipt(order, order_id)


if __name__ == "__main__":
    resuming = len(sys.argv) > 1
    session_id = sys.argv[1] if resuming else str(uuid.uuid4())

    SESSION["id"] = session_id

    if resuming:
        print(f"\n♻️  Resuming session {session_id}\n")
    else:
        print(f"\n▶️  Session {session_id}")
        print("   (save that id -- you need it to resume)\n")

    result = checkout(
        "ORD-1001", die_after_ordering=not resuming, _session_id=session_id
    )

    mine = orders_for(session_id)
    total = len(LEDGER.read_text().splitlines()) if LEDGER.exists() else 0
    print(f"\n✅ {result}")

    if resuming and EXECUTED["orders"] == 0:
        print("\n   place_order did NOT run -- replayed from the durable log.")
        if not mine:
            print(
                "   (No ledger line here for that session: it was placed by a run"
                "\n    in another directory. The engine still has the record, which"
                "\n    is why the confirmation above is the original one.)"
            )
    elif resuming:
        print(
            "\n   ⚠️  place_order DID run. That session id had no history on this"
            "\n       engine, so this started a new run rather than resuming one."
            "\n       Use the id printed by your own first run."
        )

    print(f"   this session: {len(mine)} order(s)")
    print(f"   orders.log:   {total} line(s), every run in this directory\n")
```

Two decorators are doing the work:

- `place_order` is a **`@tool`**, so the engine leases it. The shop it calls takes
  no idempotency key, like many order and booking endpoints, so calling it twice
  would place two orders.
- `build_receipt` is a **`@step`**, so its result is recorded in the session's
  graph and replayed rather than recomputed.

The `EXECUTED` counter lives inside the tool body, so the script reports what
actually happened rather than what it hopes happened. A replayed tool never
enters its body, so the count stays at zero.

## Step 4. Run it, and lose the process

```bash
python checkout_agent.py
```

```
▶️  Session 55d727b1-37bf-4524-a48a-d27b3c3b79aa
   (save that id -- you need it to resume)

   🛒 PLACED ORD-1001 for 2499 -> ord_1c57fbd87b
   💥 pod died
```

The order is placed and the engine has recorded it. Then `os._exit(17)` ends the
process before the receipt is built, which is the worst moment for a pod to go
away: the side effect has happened and the workflow has no idea.

Copy the session id. It is the only thing you need to resume.

---

## Step 5. Resume the same session

```bash
python checkout_agent.py 55d727b1-37bf-4524-a48a-d27b3c3b79aa
```

```
♻️  Resuming session 55d727b1-37bf-4524-a48a-d27b3c3b79aa

   🧾 Building receipt...

✅ {'order_id': 'ORD-1001', 'confirmation': 'ord_1c57fbd87b'}

   place_order did NOT run -- replayed from the durable log.
   this session: 1 order(s)
   orders.log:   1 line(s), every run in this directory
```

Check the ledger yourself, because the script's own reporting is not evidence:

```bash
cat orders.log
# 55d727b1-37bf-4524-a48a-d27b3c3b79aa ord_1c57fbd87b ORD-1001 2499
```

One line, after two runs.

<Check>
**The confirmation id is identical across both runs.**

`ord_1c57fbd87b` was generated by the first run, inside the tool body, and
returned to the second run without that body executing. That is replay, not
suppression. The resumed run receives the result the first run committed rather
than skipping the step and carrying on with a hole where the confirmation should
be.
</Check>

<Tip>
`_session_id` is create-or-resume, so an unknown id starts a fresh session rather
than failing. If you paste an id your engine never issued, `place_order` runs
again and the script says so. Use the id printed by your own first run.
</Tip>

---

## What you just proved

- A tool that moves something in the real world ran **at most once** across a
  crash and a restart, with no compensating logic in your code.
- The resumed run got the original result back, by the same key, rather than a
  gap it had to work around.
- Nothing was suppressed globally. Run the script fresh again and a *different*
  session places a new order, exactly as it should.

Things worth trying before you trust it:

- Resume the same id twice. Still one order.
- Restart the engine between the two runs. The session is on disk, so resuming
  after a restart behaves the same way.
